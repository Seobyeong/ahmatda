# 경로 기억 — 설계 초안

> 기준일: 2026-10-07 / 상태: **설계 초안 (코드 착수 전)**
> 관련 문서: [제품 정의서](제품-정의서.md), [표시 계층 확장 구상](표시계층-확장-구상.md)

## 1. 결정 요약

아맞다를 "외출 전 챙길 것"에서 **"외출하는 하루를 맡기는 비서"** 로 넓힌다. 다만 지도 앱이 이미 잘하는 것은 만들지 않는다.

| 하는 것 (판단 계층) | 하지 않는 것 (실행 기관에 위임) |
|---|---|
| 언제 나가야 하는지 | 경로 탐색 엔진 |
| 무엇을 챙겨야 하는지 (기존 기능) | 지도 표시, 턴바이턴 안내 |
| 이 사람의 실제 소요 시간 학습 | 환승·하차 안내 |

- **길안내**: 카카오맵·네이버지도로 **딥링크**해서 넘긴다.
- **경로**: 엔진으로 계산하지 않고 **한 번 등록한 경로를 기억**한다. 실제 걸린 시간으로 자동 보정한다.
- **실시간 정보**: 공공 버스·지하철 도착정보 API(무료)를 출발 직전에만 조회한다.
- **범위**: (a) **집 → 오늘 첫 목적지**. 이후 (b) 하루 여러 일정, (c) 전날 계획 세우기로 넓힌다. 데이터 구조는 처음부터 (b)를 수용하도록 잡는다.

경로 엔진이나 유료 경로 API(TMAP 0.88원/건, ODsay 25원/건, 2026-10-07 확인)는 사용자가 늘어 필요해지면 다시 검토한다.

---

## 2. 사용자 흐름

**처음 한 번 (경로 등록)**
1. 목적지 고르기 — "회사", "학교" 같은 이름과 위치
2. 집 근처 정류장 고르기 — 현재 위치 기준으로 가까운 정류장을 제시
3. 타는 노선 고르기 — 그 정류장을 지나는 노선 중 선택
4. 대략적인 소요 시간 확인 — 앱이 처음 추정값을 제시하고 사용자는 확인 또는 수정만 한다 (제품 원칙 2)

**매일**
1. 캘린더 일정이나 평소 출발 시각에서 오늘 외출과 **도착해야 하는 시각**을 정한다.
2. 기억한 경로와 학습값으로 **계획 출발 시각**을 계산한다 → 기존 체크리스트 알림에 함께 싣는다.
3. 출발 직전에 실시간 도착정보로 **보정**한다 → "472번 9분 후 도착, 5분 안에 나가세요".
4. [길찾기] 버튼 → 지도 앱 딥링크.
5. 집을 나서면(Wi-Fi 이탈) 실제 출발 시각을 기록한다 → 학습.

## 3. 데이터 모델 (초안)

지금은 `UserSettings.departureTime` 하나로 출발이 고정돼 있다. (b) 하루 여러 일정으로 넓힐 때 다시 뜯지 않도록 **경로(Route)** 와 **오늘의 외출(Trip)** 을 분리한다.

```ts
// 기억한 경로 — 사용자가 한 번 등록, 이후 학습값만 갱신
interface Route {
  id: string;
  name: string;                       // "회사"
  destination: { name: string; lat: number; lng: number };
  legs: RouteLeg[];                   // 지금은 도보 → 대중교통 1회 → 도보. 환승은 배열로 수용
  // 사용자가 확인한 초기 추정값 (분)
  baseMinutes: { walkToStop: number; ride: number; walkFromStop: number };
  // 실제 관측으로 누적되는 보정값 (분) — 체감온도의 learnedDelta와 같은 구조
  learnedOffsetMin: number;
  matchKeywords?: string[];           // 캘린더 일정 제목·장소와 매칭 (목적 자동감지와 같은 방식)
  updatedAt?: number;
}

interface RouteLeg {
  mode: 'bus' | 'subway';
  stop: { id: string; name: string; cityCode?: string };
  line: { id: string; name: string };
}

// 오늘의 외출 — (a)에서는 하루 1개, (b)에서는 여러 개
interface Trip {
  date: string;                       // "YYYY-MM-DD"
  routeId: string;
  eventId?: string;                   // 연결된 캘린더 일정
  arriveBy: string;                   // "HH:mm" 도착해야 하는 시각
  plannedLeaveAt: string;             // 계획 출발 시각
  actualLeftAt?: number;              // Wi-Fi 이탈로 관측한 실제 출발 시각
  arrivalFeedback?: 'late' | 'ok' | 'early';
}
```

기존 `departureTime`은 **경로가 없는 날의 기본값**으로 남긴다. 경로를 등록하지 않은 사용자에게는 지금과 똑같이 동작해야 한다.

캘린더 일정에는 장소 문자열(`location`)이 있다 (`react-native-calendar-events` 타입 정의에서 확인). 지금은 `CalendarService`가 이 필드를 버리고 있으니 함께 가져오도록 바꾼다.

## 4. 출발 시각 계산

**① 계획 단계** (전날 밤이나 아침, 실시간 정보 없이)

```
계획 출발 = 도착 시각 − (정류장까지 도보 + 대기 여유 + 탑승 + 하차 후 도보) − 학습 보정
```

**② 직전 보정 단계** (계획 출발 15~20분 전쯤)

도착정보 API로 "이 정류장에 이 노선이 몇 분 후 오나"를 조회한다.

```
실제 출발 = 버스 도착 예정 − 정류장까지 도보
```

도착정보는 보통 바로 다음 1~2대만 알려준다 (**미확인**). 그래서 아침 일찍은 ①만 쓰고, 직전에만 ②로 덮어쓴다.

## 5. 자동 보정 — 무엇으로 학습하나

'항상 허용' 위치 권한 없이 이미 있는 신호만 쓴다.

| 신호 | 어떻게 얻나 | 무엇을 학습하나 |
|---|---|---|
| **실제 출발 시각** | 기존 Wi-Fi 이탈 감지 | 계획보다 평소 몇 분 늦게·일찍 나가는지 (준비 습관) |
| **도착 피드백** | 도착 시각 이후 한 번 묻기: 늦었어요 / 딱 맞았어요 / 일찍 왔어요 | 경로 소요 시간 보정 (`learnedOffsetMin`) |

도착 피드백은 체감온도 피드백(추웠어요 / 적당했어요 / 더웠어요 → `learnedDelta` ±1)과 **같은 구조**다. 새로운 학습 방식을 만드는 게 아니라 이미 검증된 방식을 다른 축에 재사용한다.

자동 학습(외출 중 위치 기록)은 이번 범위에서 제외한다. 백그라운드 위치 권한, 배터리, 스토어 심사, 개인정보 문서 재작성 비용이 크기 때문이다.

## 6. 기술 리스크

1. **출발 직전 실시간 조회가 백그라운드에서 제때 안 돌 수 있다.** `react-native-background-fetch`는 OS가 실행 시점을 정하고(특히 iOS), 정확한 시각을 보장하지 않는다. 대응 순서:
   - MVP: 앱을 열었을 때나 알림을 탭했을 때 조회 + 계획 출발 시각 알림은 지금처럼 로컬 알림으로 확정 전송
   - 이후: 서버가 대신 조회해서 푸시 (프록시 서버를 둘 때 함께)
2. **API 키 노출.** 공공 API는 무료지만 키가 털리면 호출 한도가 소진된다. 사용자가 늘면 프록시 서버로 옮긴다.
3. **지역 커버리지.** 국토교통부 TAGO에 연계되지 않은 지자체가 있을 수 있고, 서울·경기는 별도 API를 쓰는 경우가 있다.
4. **딥링크.** 카카오맵 `by=publictransit`가 자동차 탭으로 열린다는 제보가 있다 → 실기기 확인 필요. 지도 앱 설치 여부를 확인하려면 iOS `LSApplicationQueriesSchemes`, Android `<queries>` 선언이 필요하다.

## 7. 착수 전 검증 목록

코드를 쓰기 전에 공식 문서와 실제 호출로 확인한다.

- [ ] TAGO 버스도착정보 API — 호출 한도, 응답 형식(정류장 ID, 남은 시간, 몇 대까지), 지원 도시
- [ ] TAGO 정류소 API — 좌표 기반 근처 정류장 조회 가능 여부, 정류장 경유 노선 조회
- [ ] 서울 버스·지하철 도착정보 API — TAGO와의 관계, 한도, 응답 형식
- [ ] 목적지 검색 수단 — 장소 키워드 검색 API(예: 카카오 로컬)의 무료 한도와 약관
- [ ] 딥링크 — 카카오맵·네이버지도 공식 스킴, Expo SDK 57에서 `Linking.canOpenURL` 설정 방법 (v57 문서 기준)
- [ ] 개인정보 문서 영향 — 목적지 좌표와 경로를 기기에 저장하는 것이 기존 처리방침 범위 안인지

## 8. 구현 순서 (안)

각 단계는 이전 단계 없이도 쓸모가 있게 자른다.

1. **딥링크만 먼저** — 캘린더 일정 장소로 [길찾기] 버튼 → 지도 앱. 경로 등록이 없어도 쓸모 있다.
2. **경로 등록 + 계획 출발 시각** — Route 모델, 등록 화면, ① 계획 단계 계산. 출발 알림에 반영.
3. **실시간 직전 보정** — 도착정보 API 연동, ② 보정 단계.
4. **자동 보정** — Wi-Fi 이탈 시각 기록, 도착 피드백, `learnedOffsetMin` 반영.
5. **(b) 확장** — 하루 여러 Trip, 일정 사이 이동, 지연 시 재계산.

---

## 9. 지키는 원칙

- **표시 예산**: 평소와 같으면 출발 시각 한 줄만. 버스가 늦거나 계획보다 밀렸을 때만 크게 말한다.
- **원칙 2 (확인만 한다)**: 등록 단계에서도 앱이 먼저 제안하고, 사용자는 확인·수정만 한다.
- **원칙 5 (덮어쓰기)**: 계산된 출발 시각은 언제나 사용자가 바꿀 수 있다.
- **하위 호환**: 경로를 등록하지 않은 사용자에게 기존 동작이 그대로 유지된다.
