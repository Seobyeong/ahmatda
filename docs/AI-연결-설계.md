# AI 연결 (선택 기능) — 설계 초안

> 기준일: 2026-10-14 / 상태: **BYOK(Anthropic) 구현 완료(실기기·실호출 미검증). 2026-10-14 방향 갱신 — 사전 확장·기기 AI를 앞에 두고 BYOK는 고급 설정으로(1장 "제공 방식")**
> 관련 문서: [제품 정의서](제품-정의서.md), [비서 기능 아이디어](비서-기능-아이디어.md), [표시 계층 확장 구상](표시계층-확장-구상.md)

## 1. 결정 요약

- **AI는 선택 기능이다.** 기본값은 꺼짐이다. 대부분의 사용자는 키를 넣거나 추가 비용을 낼 필요가 없어야 한다(아래 "제공 방식").
- **핵심 판단은 AI에 의존하지 않는다.** 체크리스트, 출발 알림, 체감온도, 경로 기억은 AI가 꺼져 있거나, 실패하거나, 오프라인이어도 지금과 똑같이 동작한다. AI는 로컬 판단이 **모르는 부분을 메우는 역할**만 맡는다.
- **설계 목표는 두 가지다.**
  1. **토큰 절약:** 호출하지 않는 것이 가장 싸다. 시간이 지날수록 호출 수가 0에 가까워지는 구조로 만든다.
  2. **지연 0:** 사용자가 AI 응답을 기다리는 순간을 만들지 않는다.
- **이번 범위에서 하지 않는 것**
  - MCP 서버: 서버와 계정 시스템이 생길 때 다시 검토한다.
  - Sign in with ChatGPT: 2026-10 기준 상업 앱은 선정된 파트너만 쓸 수 있는 제한 트라이얼이다.

  둘 다 5장의 `AiProvider` 인터페이스 뒤에 나중에 꽂을 수 있게 설계한다.

### 제공 방식 (2026-10-14 갱신)

**배경:** BYOK만으로는 AI 관련 직종이나 적극적인 사용자가 아니면 진입 장벽이 높다. "구독료 말고 추가 비용이 든다"는 점도 거부감을 준다. 시장 조사(2026-10-14)에서도 모바일 BYOK는 AI 채팅·일기·노트 앱에 몰려 있었다. 생활 도우미 앱이 보조 판단에만 BYOK를 붙인 사례는 찾지 못했다. 그래서 **사용자가 키도 돈도 신경 쓰지 않는 층을 앞에 둔다.**

| 층 | 방식 | 사용자 비용 | 진입 장벽 | 적용 범위 | 상태 |
|---|---|---|---|---|---|
| **1층 사전 확장** | 개발 단계에서 AI로 흔한 일정 제목을 분류하고 사람이 검수한 뒤, 로컬 키워드 사전(`calKeywords` + 일정별 준비물)으로 앱에 넣는다 | 0 | 없음 (AI인 줄도 모름) | 모든 사용자 | 미착수 |
| **2층 기기 AI** | iOS: Apple Foundation Models / Android: ML Kit Prompt API(Gemini Nano). 일정 제목이 기기 밖으로 나가지 않는다 | 0 | 켜기 한 번 | 지원 기기만 | 미착수 (8장 7·8번 검증부터) |
| **3층 BYOK** | 사용자 API 키 (Claude / OpenAI / Gemini) | 사용자 부담 | 높음 | 파워유저 | Anthropic 구현됨 |
| **(보류) 구독 포함형** | 앱 서버가 대신 호출하고, 비용은 구독료에 포함 | 구독료 안 | 없음 | 구독자 | 서버 생길 때 |

- **1층이 가장 먼저다.** "결혼식", "건강검진", "출장"처럼 사람마다 크게 다르지 않은 제목은 사전으로 끝낸다. 3장의 L0가 걸러내는 범위가 넓어지므로, 2·3층의 호출 자체가 줄어든다. 사전에 없는 개인 일정은 기존처럼 L2 학습 승격으로 쌓는다.
- **2층과 3층은 함께 구현한다.** 둘 다 같은 `AiProvider` 뒤에 둔다. 설정 화면은 지원 기기면 "기기 AI로 더 똑똑하게 [켜기]"를 기본으로 보여주고, 지원하지 않는 기기에서는 이 항목을 숨긴다. BYOK는 설정 > 고급 > "내 AI 계정 연결"로 옮기고, "API 키"라는 말은 고급 화면 안에서만 쓴다.
- **둘 다 켜져 있으면 기기 AI를 먼저 쓴다.** 비용이 0이고 데이터가 기기 밖으로 나가지 않기 때문이다. 기기 AI가 쓸 수 없는 상태(모델 미다운로드 등)일 때만 BYOK로 넘어간다. 기기 AI 결과가 "모름"일 때 BYOK로 다시 물을지는 품질 비교(8장 1·8번) 뒤에 정한다.
- **구독 포함형은 선택지로 남겨둔다.** 사용자 경험은 가장 깔끔하다. 다만 서버, 키 보호, 사용자별 사용량 제한, 악용 방지가 새로 필요하다. 서버와 계정이 생기면 MCP 재검토와 함께 본다. 1·2층을 적용한 뒤에도 미분류 일정이 얼마나 남는지가 판단 근거다. 이 방식은 `AiProvider` 구현 하나(`hosted`)로 들어오므로, 지금 구조를 바꿀 필요는 없다.

## 2. AI에게 맡기는 일

### 1단계 (2026-10-14 확정): 키워드에 안 걸리는 일정 해석

지금은 `detectPurposeFromEvents`가 일정 제목에 키워드가 **포함되는지**만 본다. 키워드는 `PURPOSES[*].calKeywords`에 사용자의 `customKeywords`를 더한 것이다. 그래서 "부산 출장", "결혼식", "건강검진"처럼 키워드에 없는 일정은 목적이 감지되지 않고, 준비물 제안도 비어 있게 된다.

AI는 **로컬 매칭에 실패한 일정 제목에 대해서만** 다음 두 가지를 돌려준다.

- 목적 분류: 기존 5개 `PurposeId` 중 하나, 또는 해당 없음(`null`)
- 그 일정에만 필요한 추가 준비물: 최대 3개, 짧은 라벨

| 일정 제목 | 로컬 매칭 | AI 결과 (예시) |
|---|---|---|
| 팀 회의 | work (키워드 "회의") | 호출 안 함 |
| 부산 출장 | 없음 | work + 신분증, 충전기 |
| 친구 결혼식 | 없음 | null + 축의금 봉투 |
| 건강검진 | 없음 | null + 신분증 |

### 넣지 않는 것 (권장)

- **"내일 뭐 챙겨?" 같은 대화형 질문:** 답은 이미 로컬 판단에 있다. AI는 문장을 만들어줄 뿐이라 토큰 대비 가치가 낮다. 이 역할은 나중에 MCP 방향에서 **사용자가 쓰는 AI 쪽**이 맡는 게 맞다.
- **자연어 빠른 추가** ("우산이랑 도시락 추가"): 대부분 로컬 파싱으로 된다. 필요성이 확인되면 2단계에서 검토한다.

## 3. 토큰 절약 — 호출을 줄이는 6개 층

위에서부터 차례로 걸러내고, 마지막까지 남은 것만 API로 보낸다.

| 층 | 방법 | 효과 |
|---|---|---|
| **L0 안 부르기** | 로컬 키워드 매칭에 걸리는 일정은 AI에 보내지 않는다. 지난 일정도, 오늘·내일 밖의 일정도 보내지 않는다. | 대부분의 일정이 여기서 걸러짐 |
| **L1 결과 캐시** | 정규화한 제목(공백 정리·소문자)을 키로 결과를 저장한다. 같은 제목이 다시 나오면 캐시를 쓴다. | 반복 일정("PT 수업", "주간 보고")은 첫 1회만 호출 |
| **L2 학습 승격** | 사용자가 AI 분류를 받아들이면 그 제목을 해당 목적의 `customKeywords`에 추가한다. 이후로는 L0에서 처리된다. 거절하면 "AI 결과 없음"으로 캐시해서 다시 묻지 않는다. | 쓸수록 AI 호출이 0에 수렴. 체감온도 `learnedDelta`와 같은 "개인화로 수렴" 구조 |
| **L3 묶음 호출** | 남은 미분류 일정을 하루 단위로 **한 번의 요청**에 담는다. | 고정 프롬프트 비용을 일정 수로 나눔 |
| **L4 최소 입력** | **일정 제목만** 보낸다. 시간·장소·참석자·메모·위치·날씨는 보내지 않는다. | 토큰과 개인정보 노출을 동시에 줄임 (6장 동의 범위도 좁아짐) |
| **L5 최소 출력** | 구조화 출력(JSON 스키마)을 쓴다. 목적은 enum, 준비물은 최대 3개·각 10자 이내, 설명 문장은 없다. `max_tokens`도 작게 잡는다. | 출력 토큰은 입력보다 단가가 높아서(Claude 기준 5배) 가장 효과가 큼 |

**L6 상한:** 앱 안에 하루 호출 수 상한을 둔다(기본값은 예를 들어 하루 3회, 실제 값은 나중에 정함). 설정 화면에는 이번 달 호출 수를 보여준다. 키가 잘못 설정되거나 버그가 나도 요금 폭주가 일어나지 않게 막는 장치다.

### 하지 않는 최적화와 그 이유

- **프롬프트 캐싱:** 최신 Claude 모델은 **512토큰 미만의 접두부를 캐싱하지 않는다**(Claude API 스킬 문서 기준). 이 기능의 요청은 그보다 훨씬 짧다. 캐싱 구조를 만들 게 아니라 고정 프롬프트 자체를 짧게 유지하는 것이 맞다.
- **추론(thinking) 토큰:** Claude Haiku 5.5는 adaptive thinking이 기본으로 켜져 있고, 추론 토큰은 출력으로 과금된다. 단순 분류에는 필요 없을 가능성이 크다. **effort `low` 또는 thinking 끄기**(Haiku 5.5는 effort `high` 이하에서만 끌 수 있음)를 8장 검증으로 확인한 뒤 정한다.

### 비용 감 잡기 (가정치)

요청 1회의 입력 300토큰, 출력 100토큰을 가정한다. 실제 값은 구현 후 `usage`로 측정한다.

| 모델 (Claude 공식가, 2026-10) | 입력 $/1M | 출력 $/1M | 1회 비용 |
|---|---|---|---|
| Claude Haiku 5.5 | 0.10 | 0.50 | 약 $0.00008 |
| Claude Sonnet 5.5 | 2.00 | 10.00 | 약 $0.0016 |
| Claude Opus 5.5 | 4.00 | 20.00 | 약 $0.0032 |

L0~L3이 제대로 동작하면 하루 0~1회 수준이 된다. OpenAI·Gemini 저가 모델도 단가가 비슷한 수준이다(8장 3번).

> **[결정 필요]** 제공자별 기본 모델. 이 작업은 분류 성격이라 작은 모델이 맞을 가능성이 높다. 다만 8장의 작은 평가셋으로 품질을 확인한 뒤 고른다. 사용자가 설정에서 바꿀 수 있게 할지도 함께 정한다.

## 4. 지연 0 — 사용자가 기다리지 않는 구조

**규칙 1. 사용자 동선에서 AI를 `await`하지 않는다.**
화면과 알림은 항상 로컬 결과로 즉시 그린다. AI 결과는 **미리 계산해서 캐시에 넣어두고**, 화면은 캐시를 읽기만 한다.

**규칙 2. 미리 계산하는 시점**

| 시점 | 대상 |
|---|---|
| 앱이 일정을 불러온 직후 (대시보드 진입) | 오늘 남은 미분류 일정 — 화면은 먼저 그리고, 호출은 뒤에서 |
| 백그라운드 fetch (`BackgroundTaskService`, 최소 15분 간격) | 내일 일정 — 전날 밤에 처리해두면 아침에 캐시가 이미 차 있음 |

현재 `CalendarService.getTodayEvents()`는 오늘 일정만 가져온다. 내일 일정을 미리 처리하려면 날짜 범위를 인자로 받도록 확장해야 한다.

**규칙 3. 늦게 온 결과는 덧붙이기만 한다.**
사용자가 체크하는 도중에 결과가 도착하면 목록을 재정렬하지 않는다. 맨 아래에 "일정 기반 제안" 묶음으로 추가하고, 수락·거절 버튼을 둔다. 체크 중에 목록이 움직이면 잘못 누르는 사고가 난다.

**규칙 4. 출발 알림 경로에서는 AI를 호출하지 않는다.**
`BackgroundTaskService._runCheck` 같은 알림 판단 경로는 캐시만 읽는다. 알림 시각은 AI 응답 시간과 무관해야 한다.

**규칙 5. 짧은 타임아웃, 재시도는 다음 기회에.**
요청 타임아웃은 짧게 잡는다(예: 8초, 측정 후 조정). 실패하면 그 자리에서 재시도하지 않고 다음 미리 계산 시점에 다시 시도한다. 직접 `fetch`로 호출하므로 자동 재시도는 없다.

Claude 구조화 출력은 **새 스키마를 처음 쓸 때 컴파일 지연이 한 번** 생기고, 이후 24시간 동안 캐시된다. 스키마는 앱 버전마다 고정하고, 첫 호출이 느려도 미리 계산 단계에서 일어나므로 사용자에게는 보이지 않는다.

## 5. 구조

```ts
// 제공자 교체 가능 — 기기 AI 2종, BYOK 3종. 나중에 구독 포함형(hosted)·Sign in with ChatGPT도 같은 자리에
interface AiProvider {
  id: 'apple-on-device' | 'gemini-nano' | 'anthropic' | 'openai' | 'gemini';
  kind: 'on-device' | 'byok';  // 동의 문구·상한·실패 처리가 kind에 따라 갈림
  isAvailable(): Promise<boolean>;  // 기기 AI: 지원 기기 + 모델 준비 여부. BYOK: 키 존재 여부
  // 미분류 일정 제목 묶음 → 제목별 결과. 실패 시 throw (호출부가 조용히 무시)
  classifyEvents(titles: string[], signal: AbortSignal): Promise<EventHint[]>;
}

interface EventHint {
  title: string;              // 정규화 전 원문 (화면 표시용)
  purposeId: PurposeId | null;
  extraItems: string[];       // 최대 3개
}

// persist 대상 — 정규화 제목 → 결과
interface AiHintCacheEntry {
  hint: EventHint | null;     // null = "AI도 모름" 또는 사용자가 거절 → 다시 묻지 않음
  status: 'pending' | 'accepted' | 'rejected';
  createdAt: number;
}
```

- **판단 계층과의 경계:** `detectPurposeFromEvents`는 지금처럼 키워드만 본다. AI 결과는 사용자가 수락하는 순간 `customKeywords`로 들어가므로, 판단 계층은 AI의 존재를 알 필요가 없다. 추가 준비물은 오늘만 쓰는 임시 항목(`temp: true`)으로 넣는다.
- **SDK를 쓰지 않고 `fetch`로 직접 호출한다.** Anthropic·OpenAI 공식 TS SDK는 README에 "React Native is not supported"라고 명시돼 있다. Gemini SDK(`@google/genai`)는 RN을 언급하지 않는다(8장). 필요한 요청은 엔드포인트 하나에 JSON 본문 하나라서 직접 호출해도 코드가 작고, 번들도 늘지 않는다.
- **결과 검증은 앱이 한다.** 구조화 출력은 `maxItems`를 지원하지 않는다. 그래서 준비물 3개 제한, 라벨 길이, 목적 enum은 응답을 받은 뒤 앱에서 다시 확인하고 잘라낸다.
- **캐시 키는 제목의 해시다.** 개인정보처리방침상 캘린더 일정은 기기에도 저장하지 않으므로, 캐시는 정규화한 제목의 해시(64비트 FNV-1a)를 키로 쓰고 제목 원문은 남기지 않는다. 제목은 화면 상태에서만 쓴다. 예외는 사용자가 제안을 **수락**했을 때뿐이다. 이때 제목이 `customKeywords`에 들어가며, 이 키워드는 설정에서 보이고 지울 수 있다.
- **기기 AI도 같은 캐시와 층을 거친다.** 비용은 0이지만 배터리와 처리 시간이 들기 때문에 L0~L3은 그대로 적용한다. L6 하루 상한은 기기 AI에서는 비용 보호용이 아니라 배터리 보호용이므로, 값을 따로 둔다. 구조화 출력은 Apple은 guided generation, Gemini Nano는 프롬프트 지시로 처리하고, 어느 쪽이든 앱이 결과를 다시 검증한다(위 항목). 각 방식의 실제 지원 범위는 8장 7번에서 확인한다.
- **캐시 크기:** 180일이 지나면 만료되고, 최대 300개까지 둔다. 수락한 항목도 캐시에 남는다. 목적 없이 준비물만 있는 제안은 키워드로 승격할 수 없으므로, 다음에 같은 일정이 오면 캐시에서 다시 제안한다(호출 없음).

## 6. 키 보관과 동의

**키 보관**
- 키는 보안 저장소(iOS Keychain / Android Keystore)에 둔다. AsyncStorage와 Zustand persist에는 넣지 않는다.
- `expo-secure-store`를 쓴다(`npx expo install expo-secure-store`, v57 문서 확인).
  - Android: Keystore로 암호화해 SharedPreferences에 저장한다. 이 앱은 `android:allowBackup="false"`라 백업 복원 문제가 없다. bare workflow라 config plugin이 적용되지 않는데, 그래도 백업 설정을 따로 손볼 필요가 없다.
  - iOS: Keychain에 저장한다. 생체 인증(`requireAuthentication`)은 쓰지 않는다. 그러면 `NSFaceIDUsageDescription`은 필요 없을 것으로 보이는데, 문서는 bare에서 수동 추가하라고만 적고 있다 → 구현할 때 iOS 빌드로 확인한다.
  - `keychainAccessible`은 기본값 `WHEN_UNLOCKED`로 둔다. 다만 백그라운드 fetch에서 잠금 상태일 때 키를 읽어야 하면 `AFTER_FIRST_UNLOCK`이 필요하다(4장 규칙 2와 연결, 구현 시 결정).
  - iOS는 값이 약 2048바이트를 넘으면 거부한 사례가 있다. API 키는 이보다 작다.
- 키는 로그·에러 리포트·동기화 대상에서 제외한다.

**동의 (iOS 심사 5.1.2(i), 원문 확인 2026-10-14)**
- 원문: *"You must clearly disclose where personal data will be shared with third parties, including with third-party AI, and obtain explicit permission before doing so."*
- **Gemini 무료 키 주의:** Gemini API 무료 등급은 입력·출력을 Google 제품 개선에 쓰고 사람이 검토할 수 있다. 약관도 "개인 정보는 무료 서비스에 보내지 말라"고 적고 있다. 유료 등급은 학습에 쓰지 않는다. 그래서 Gemini를 고르면 동의 화면에 **"무료 키를 쓰면 일정 제목이 Google의 제품 개선에 사용될 수 있습니다"**를 따로 표시한다.
- **Gemini 나이 조건:** Gemini API 약관은 18세 이상만 쓸 수 있고, 18세 미만이 접근할 가능성이 높은 앱에는 쓸 수 없게 한다. 앱 연령 등급과 맞는지 출시 전에 확인한다.
- 앱 안 동의 화면에 넣을 내용:
  - "캘린더 일정 **제목**이 [선택한 제공자]로 전송됩니다"
  - 보내지 않는 것: 시간, 장소, 메모, 위치
  - 언제 끌 수 있는지
- 동의 전에는 호출하지 않는다. 제공자를 바꾸면 다시 동의를 받는다.
- **기기 AI는 외부 전송 동의 대상이 아니다.** 일정 제목이 기기 밖으로 나가지 않으므로 5.1.2(i)의 "제3자 공유"에 해당하지 않는다고 본다(해석, 출시 전 재확인). 그래도 켤 때 "일정 제목을 기기 안에서 분석합니다. 외부로 보내지 않습니다" 한 줄은 보여준다. 이 문구가 BYOK와의 차이를 설명하는 역할도 한다.
- **구독 포함형을 도입하면** 전송 대상이 "아맞다 서버 → AI 제공자"가 되므로, 동의 문구와 개인정보처리방침에 서버 처리와 보관 기간을 새로 넣어야 한다.
- 함께 고칠 문서: 개인정보처리방침, App Store 개인정보 라벨, Play 데이터 보안 섹션.

## 10. 지키는 원칙

- AI가 없어도 앱은 완전하다. AI는 덧붙이기만 하고 대체하지 않는다.
- 사용자에게 키나 추가 비용을 요구하는 방식은 마지막 층이다. 사전과 기기 AI로 해결할 수 있으면 거기서 끝낸다.
- 가장 싼 호출은 하지 않는 호출이다. 한 번 배운 것은 다시 묻지 않는다.
- 사용자는 AI를 기다리지 않는다. 알림 시각은 AI와 무관하다.
- 보내는 데이터는 일정 제목 하나로 한정하고, 보내기 전에 동의를 받는다.

## 11. 템플릿 개인화 — 사용자가 구독 중인 AI로 (2026-10-14 합의)

**문제:** 초기 개인화(루틴, 키워드, 출발 시각을 사람에 맞추는 일)를 AI 대화로 하면, 대화가 길어서 앱의 API로는 가장 비싼 기능이 된다. 그리고 BYOK는 일반 사용자에게 진입 장벽이 된다.

**방식:** 앱은 **템플릿(프롬프트)만 제공**하고, 대화는 사용자가 이미 구독 중인 AI 앱(ChatGPT, Claude, Gemini 등)에서 한다. AI가 정해진 형식의 결과 블록을 출력하면, 사용자가 그것을 앱에 붙여넣는다. 앱은 미리보기를 보여주고, 사용자가 적용을 누르면 반영한다.

| | 기존 BYOK (2~9장) | 템플릿 개인화 |
|---|---|---|
| 비용 | 사용자 API 요금 | 0 (구독에 포함) |
| 키 | 필요 | 불필요 |
| 앱의 외부 전송 | 일정 제목 (동의 필요) | **없음** — 사용자가 자기 AI 앱에 직접 입력 |
| 자동 실행 | 백그라운드 가능 | 불가 — 사람이 대화하는 구조 |
| 용도 | 매일 새로 생기는 미분류 일정 | 처음 한 번 + 생활이 바뀔 때 |

두 방식은 서로를 대체하지 않는다. 템플릿 개인화로 키워드와 루틴을 처음부터 채워두면, 키워드에 안 걸리는 일정 자체가 줄어서 BYOK 호출도 함께 준다.

**범위 (1차): 지금 데이터 구조로 되는 것만**

| 필드 | 반영 방식 |
|---|---|
| `departureTime` | 바꿈 (미리보기에 이전 → 이후 표시) |
| `sensitivity` (1~5) | 바꿈. 피드백으로 쌓인 학습값 `learnedDelta`는 건드리지 않음 |
| `routines` (라벨 + 요일) | **추가만.** 같은 라벨의 루틴이 이미 있으면 건너뜀 |
| `keywords` (목적별) | **추가만.** 기본 키워드나 이미 있는 키워드는 건너뜀 |
| `disabledPurposeItems` (목적별) | 기본 준비물 중 실제로 존재하는 라벨만 끔 |

"목적별 준비물 직접 추가"와 "새 목적 만들기"는 데이터 구조 확장이 먼저 필요하다 → 2차.

**안전장치:** 붙여넣은 텍스트는 신뢰할 수 없는 입력으로 다룬다.
- 데이터로만 해석한다.
- 텍스트 안에서 `"ahmatda": 1`이 든 JSON 블록만 찾는다. 코드블록이나 스마트 따옴표가 섞여도 읽는다.
- 모르는 필드는 무시한다.
- 개수와 길이에 상한을 둔다.
- 기존 값은 지우지 않는다.
- 적용 전에 반드시 미리보기를 보여준다.

**진입점:** 설정 → "AI로 개인화하기"
- [템플릿 보내기]는 OS 공유 시트를 연다. 사용자가 AI 앱을 직접 고르고, 새 의존성은 없다.
- [결과 붙여넣기] → 미리보기 → 적용.
- 프롬프트가 미리 채워진 "ChatGPT에서 열기" 같은 링크는 서비스별 URL 형식을 검증하지 않아서 넣지 않았다.

**구현 (2026-10-14):**
- `services/personalize/template.ts`: 템플릿 생성. 목적과 기본 준비물은 `PURPOSES`에서 만들어서 라벨이 항상 일치한다.
- `importPlan.ts`: 파서와 계획 생성. 템플릿 자체를 붙여넣으면 거부한다 — 안 그러면 예시 값이 실제 결과처럼 들어간다. 테스트 11개.
- 화면: 설정 → `PersonalizeModal`(공유 시트 → 붙여넣기 → 미리보기 → 적용)
- store: `applyPersonalization`
