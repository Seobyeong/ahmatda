# 아맞다 — 계정 도입 로드맵

> 계정을 언제, 왜, 어떤 순서로 붙일지 — 그리고 붙이지 않아도 되는 것은 무엇인지 정리한 설계 메모.
> 기준일: 2026-09-16
> 관련 문서: [제품 정의서](제품-정의서.md) (5.5 외부 데이터, 6.3 수익 모델)

---

## 0. 전제 — 이건 바뀌지 않는다

1. **앱은 계정 없이 100% 동작한다.** 계정은 기능을 여는 열쇠가 아니라 데이터를 지키는 옵션이다. 로그인해야 쓸 수 있는 기능이 하나라도 생기면 접근성 원칙이 무너진다.
2. **온보딩에 로그인을 넣지 않는다.** 설치 직후는 이탈이 가장 심한 구간이고, 그 시점의 사용자는 앱이 뭘 해주는지 아직 모른다.
3. **계정은 "가입"이 아니라 "백업 켜기"로 등장한다.** 사용자가 계정의 필요를 스스로 느낀 뒤에 제안한다.

---

## 1. 계정이 있어야만 되는 것

기기 로컬로는 원리적으로 불가능한 것들. 계정을 만드는 진짜 이유는 여기에 있다.

### 1.1 학습 데이터 백업·복원 (가장 근본)

이 앱의 가치는 Δt 보정치와 놓침 이력처럼 **몇 주에 걸쳐 쌓인 개인 데이터**다. 그런데 지금은 그게 전부 기기 안에만 있다.

- 기기를 바꾸면 처음부터 다시 학습한다 — 신규 사용자와 같은 상태로 되돌아간다
- 앱을 잠깐 지웠다 깔면 그동안의 개인화가 사라진다
- 사용자가 "지우면 다 날아가는구나"를 알면 앱을 지우지 못하는 게 아니라 **애초에 깊게 쓰지 않는다**

> 차별점이 "복사할 수 없는 개인 데이터"라면, 그 데이터가 기기 초기화 한 번에 사라지는 건 제품 논리의 구멍이다.

### 1.2 공유 체크리스트 — 가족·룸메이트·커플

이미 구독 영역으로 구상해둔 기능이고, 계정이 없으면 한 줄도 만들 수 없다.

- 여행 준비물을 둘이 나눠 챙기고 **누가 뭘 챙겼는지 실시간으로 보이는 것** — 이 앱 형식이 가장 잘 맞는 상황이다
- 공용 물건(집 열쇠, 우산, 아이 준비물)은 원래 한 사람 것이 아니다
- **초대가 곧 유입이다.** 초대받은 사람이 앱을 깔아야 하므로, 유일하게 자연스러운 바이럴 경로가 된다

### 1.3 다기기 — 폰 + 태블릿 + 워치

특히 워치는 이 앱과 궁합이 좋다. 나가기 직전에 손목에서 체크하는 게 폰을 꺼내는 것보다 빠르고, 그게 원칙 1(속도 > 정교함)에 정확히 부합한다. 다만 워치는 별도 기기라 동기화 없이는 시작할 수 없다.

### 1.4 구독 상태 (수익화 시점)

구독을 도입하면 계정은 사실상 필수다. 기기에만 결제 상태가 있으면 폰을 바꿨을 때 결제한 사람이 기능을 잃는다. 스토어 복원만으로는 부족하다.

## 2. 계정이 있으면 좋아지는 것

없어도 동작하지만, 있으면 개인화의 질이 달라지는 것들. 전부 **익명 집계**를 전제로 한다.

### 2.1 콜드 스타트 해결 — 남의 데이터로 시작하기

신규 사용자는 Δt가 0에서 시작해 몇 주를 기다려야 한다. 그런데 **비슷한 민감도를 고른 사람들의 수렴값**을 초기값으로 주면 첫날부터 꽤 맞는 추천이 가능하다.

- "민감도 4단계 + 대중교통 이용자"의 평균 Δt = 첫날 시드
- 온보딩 문항을 더 줄일 수 있다 — 물어볼수록 정확해지는 게 아니라, 집단 데이터가 물음을 대신한다
- 개인 응답이 쌓이면 집단값의 가중치는 자연히 내려간다

### 2.2 지역 보정

같은 12°C라도 서울과 부산의 체감이 다르고, 같은 도시 안에서도 바람길에 따라 다르다. 격자(nx, ny) 단위로 "이 지역 사람들은 예보 대비 평균 몇 도를 더 춥게 느끼는지"를 집계하면 기상청 값 자체를 보정할 수 있다. **기기 하나로는 절대 만들 수 없는 데이터다.**

### 2.3 준비물 추천 학습

지금 목적별 준비물은 고정 리스트다. 계정이 있으면 "같은 목적을 고른 사람들이 자주 추가하는 항목"을 제안할 수 있다.

- 운동·헬스에 `사물함 열쇠`를 많이 넣는다면 기본 목록에 후보로 올린다
- 반대로 대부분이 끄는 항목(`disabledWeatherItems`에 자주 들어가는 것)은 기본에서 뺀다 — **이미 저장 중인 데이터라 추가 수집이 없다**

## 3. 서버에 딸려오는 것

계정 자체와는 별개지만, 서버가 생기는 순간 같이 가능해지는 것들. 일부는 계정보다 이득이 크다.

### 3.1 서버 푸시로 앱 깨우기

지금 알림은 전부 **로컬** 알림이라, 앱을 스와이프 종료하면 Wi-Fi 이탈 감지와 백그라운드 폴링이 같이 멈춘다. 제품 정의서 4.5에 "의도적 한계"로 적어둔 부분이다.

서버가 생기면 출발 시각 근처에 데이터 푸시를 보내 **앱을 깨워서 `checkOnce()`를 돌릴 수 있다.** 종료 상태를 완전히 뚫는 건 아니지만, 현재 구조에서 남은 가장 큰 구멍을 실질적으로 줄인다. **계정 없이도 기기 토큰만으로 가능하다.**

### 3.2 API 키 보호 + 호출량 절감

지금 `EXPO_PUBLIC_KMA_API_KEY`는 앱 번들에 그대로 들어간다. 무료 키지만 쿼터가 있고, 추출해서 남이 쓰면 **내 앱이 먼저 죽는다.**

- 서버 프록시로 옮기면 키가 노출되지 않는다
- 같은 격자를 보는 사용자끼리 **서버 캐시를 공유**한다 — 같은 지역 사용자 1,000명이 각자 호출하던 것이 한 번으로 줄어든다
- 사용자가 늘수록 이득이 커지는 구조라, 지금은 아니어도 언젠가는 필요하다

### 3.3 효과 지표를 개발자가 볼 수 있게 됨

지금 구조에서 "주간 놓침 횟수 감소폭"(제품 정의서 6.4)은 **사용자 본인만 볼 수 있다.** 서버가 없어 집계가 불가능하기 때문이다. 익명 집계가 가능해지면 제품 개선 근거와 투자·지원사업 설명 자료가 동시에 생긴다.

## 4. 도입 순서

각 단계는 앞 단계 없이 시작할 수 없다.

| 단계 | 내용 | 얻는 것 |
|---|---|---|
| **0 (현재)** | 계정 없음 — 기기 로컬. 선행 정비만 완료 | — |
| **1** | **익명 백업** — 기기 식별자로 자동 생성되는 계정. **로그인 화면이 없다.** 설정에 "백업 켜기" 스위치 하나 | 1.1 복원, 3.1 푸시, 3.2 키 보호 |
| **2** | **계정 연결** — Apple·Google 로그인만, 비밀번호 없음. **기기를 바꿀 때만** 필요하므로 그 순간에만 안내 | 기기 이전 |
| **3** | **공유** — 공유 체크리스트. 삭제 동기화 설계가 여기서 처음 필요해진다 | 1.2, 유입 경로 |
| **4** | **집단 학습 · 구독** — 유지율이 확보된 뒤에 | 2.1, 2.2, 1.4 |

**1단계를 로그인 없이 만드는 게 전부다.** 익명 계정은 사용자 입장에서 스위치 하나지만, 서버 입장에서는 이미 완전한 계정이다. 이렇게 하면 접근성을 하나도 깎지 않고 1.1·3.1·3.2를 전부 가져간다. 로그인은 **기기를 바꾸는 사람에게만**, 그 순간에 필요해진다.

## 5. 넘어야 할 것

### 삭제 동기화 (tombstone)

지금 구조로 두 기기 데이터를 그냥 합치면 **A에서 지운 루틴이 B에서 부활한다.** "없음"은 "지웠음"과 "아직 못 받았음"을 구분하지 못하기 때문이다. 삭제 기록(`deletedAt`)을 남기는 설계가 필요한데, 스키마와 병합 로직을 같이 건드려야 해서 **3단계(공유)를 실제로 만들 때** 하는 게 맞다. 지금 미리 넣을 필요는 없다.

### 서버로 보내면 안 되는 데이터

- **집 Wi-Fi BSSID** — 공개 DB와 대조하면 집 위치를 특정할 수 있다. 기기 로컬에만 둔다 (`partialize` 주석에 명시해둠)
- **놓침 이력·피드백** — 개인 식별 상태로는 생활 패턴 데이터로 읽힌다. 백업은 개인 소유로, **집계는 익명으로** 분리한다
- **캘린더 일정 제목** — 목적 감지에 쓰고 나면 절대 밖으로 내보내지 않는다. 지금도 그렇고 계정이 생겨도 그대로다

### 스토어 문서 재작성

서버가 생기는 순간 `legal/privacy-policy.ko.md`, Google Play 데이터 안전성, Apple App Privacy를 **전부 다시 써야 한다.** 지금 "기기 밖으로 안 나감"이라고 단순하게 쓸 수 있는 게 실질적 이점이므로, **출시 전에는 계정을 넣지 않는 편이 낫다.**

### 운영 비용이 0에서 벗어난다

서버 한 대라도 생기면 고정비와 장애 대응 책임이 함께 생긴다. 1단계는 관리형 백엔드(인증 + 문서 DB + 푸시)로 시작해 직접 운영을 최대한 미루는 게 좋다.

## 6. 선행 정비 (2026-09-16 적용 완료)

계정을 나중에 붙일 때 비싸지는 부분을 미리 정리했다. 전부 계정 없이도 유효한 변경이다.

| 변경 | 위치 | 이유 |
|---|---|---|
| persist `version` / `migrate` | `store/index.ts` | 스키마 변경 대응. 출시 후엔 version 없는 데이터가 이미 깔려 구분 불가 |
| 아이템 id `number` → `string` (UUID) | `types`, `store`, 컴포넌트 3곳 | 두 기기에서 만든 항목의 id 충돌 방지. 공유 체크리스트의 전제 |
| 기본 루틴 고정 id | `DEFAULT_ROUTINES` | 두 기기가 각자 기본값에서 시작해도 '집 열쇠'가 둘로 늘지 않게 |
| `updatedAt` 필드 | `ChecklistItem`, `UserSettings`, `FeedbackRecord` | 동기화 충돌 해결(last-write-wins)의 판단 근거 |
| `patchSettings()` 경유 통일 | `store/index.ts` | userSettings 변경 경로 10곳이 `updatedAt`을 빠뜨릴 수 없게 |
| 동기화 대상 구분 주석 | `partialize` 상단 | 무엇을 서버에 올리고 무엇을 기기에 둘지 미리 확정 |

**`ForgottenRecord`에 `updatedAt`을 넣지 않은 건 의도적이다.** 사용자가 고치는 값이 아니라 기기가 관측한 사실이라, 날짜 기준 합집합이면 충분하고 충돌 해결 대상이 아니다.

**UUID를 의존성 없이 직접 만든 이유**: `expo-crypto`를 추가하면 Bare Workflow라 네이티브 재빌드가 필요하다. 여기서 필요한 건 암호학적 안전성이 아니라 유일성뿐이라 `Math.random` 기반 RFC 4122 v4 형식으로 충분하다.

### 남은 확인

`tsc --noEmit` 통과, 유닛테스트 50개 통과. 다만 **실기기에서 기존 설치를 지우지 말고 업데이트 설치**해서 마이그레이션(숫자 id → 문자열)이 실제로 도는지 확인해야 한다. 지우고 새로 깔면 `migrate`가 아예 불리지 않아 검증이 되지 않는다.
